# TOON Tools Agent Instructions

These instructions apply repository-wide. A nested `AGENTS.md` narrows or adds rules for its subtree; the closest applicable file wins for scoped implementation details.

Nested instructions must not weaken workspace-trust, webview security, package integrity, release, evidence, or branch-governance constraints unless the underlying repository policy is intentionally changed in the same pull request.

## Repository purpose

TOON Tools is a VS Code extension for the TOON data format. The shipped product lives in the repository root package and bundles production code from `src/**` into `dist/extension.js`.

The main execution and governance boundaries are:

- `src/AGENTS.md` — extension runtime, parser/formatter/linter behavior, workspace trust, webviews, commands, filesystem writes, and public extension contracts.
- `scripts/AGENTS.md` — repository policy checks, packaging, release verification, bundle/performance baselines, and marketplace helpers.
- `.github/AGENTS.md` — CI, branch governance, security automation, release/publish workflows, permissions, and provenance.

Do not create one instruction file per feature directory. Add another boundary only when authority or release/security semantics materially differ.

## Read first

Before changing behavior, read the affected source/tests plus:

- `README.md`
- `docs/toon-spec.md`
- `docs/contributing.md`
- `docs/automation.md`
- `docs/publishing.md`
- `docs/repository-rules.md`
- `SECURITY.md`

## Product truth

- Do not claim support for TOON syntax or conversions beyond the parser/spec/tests actually implemented.
- Keep parser, formatter, linter, rename/definition, preview, table-viewer, CSV export, and conversion semantics aligned with `docs/toon-spec.md`.
- Do not invent benchmark, coverage, mutation, marketplace, security-scan, or release results.
- A generated VSIX or local smoke is not evidence that both marketplaces published successfully.

## Toolchain

Use the repository-pinned Node and pnpm versions.

```bash
corepack enable
pnpm install --frozen-lockfile --config.ignore-scripts=true
pnpm run format:check
pnpm run lint
pnpm run typecheck
pnpm run test:unit
pnpm run build
```

The complete CI-equivalent gate is:

```bash
pnpm run check:ci
```

Do not weaken coverage, mutation, bundle-size, performance, workspace-trust, package-content, dependency, or release checks to land unrelated changes.

## Architecture and generated state

- Production source is under `src/**`; tests under `test/**`.
- `dist/**` is generated by Webpack. Do not hand-edit it.
- TextMate grammars, snippets, schemas, icons, media, package contribution metadata, and docs are public package surfaces.
- Command IDs/settings/views must stay aligned across `package.json`, activation/registration code, tests, and documentation.
- Update generated or baseline files only through their owning script and only when the semantic change is intentional.

## Security

- Untrusted workspaces are supported only in the limited mode declared in `package.json`.
- State-changing conversion/export behavior must preserve runtime workspace-trust checks; menu visibility alone is not a security control.
- All webviews must keep restrictive CSP, crypto-safe nonces, minimal `localResourceRoots`, and escaped untrusted content. Never add `unsafe-inline`, `unsafe-eval`, `eval`, or dynamic code execution.
- Validate paths and document content before writing or exporting.
- Do not log or commit marketplace tokens, release credentials, private keys, environment secrets, or sensitive local paths.

## Package and release integrity

- Repository-only governance files, source, tests, scripts, locks, and local tooling must stay out of the VSIX.
- Keep `.vscodeignore` and `scripts/check-package-contents.js` aligned.
- Publishing is owned by GitHub Actions and the protected `marketplace` environment.
- Release Please owns release PR/tag creation.
- The VSIX, checksums, SBOM, provenance, GitHub Release assets, VS Code Marketplace version, and Open VSX version must refer to the same release identity.
- Do not replace released bytes or manually publish a different build under an existing version.

## Change discipline

- Keep diffs single-purpose.
- Add focused regression tests for parser, conversion, trust, webview, export, package, or release fixes.
- Preserve cross-platform behavior across the required Linux, Windows, and macOS CI matrix.
- Do not bypass required reviews, status checks, rulesets, or release validation.

## Definition of done

A change is ready when focused tests and the appropriate repository gates pass, package contents remain intentional, docs/public metadata match behavior, no actionable review finding remains unresolved, and any environment-dependent validation that did not run is reported precisely.
